# CNV 板布局工具：架构审查与重构记录

## 结论

这个工具的本质是一个“输入实验配置 → 生成确定性板布局 → 计算配液 → 导出文件”的本地计算器。它不需要服务端渲染、数据库、鉴权、Worker 或全栈框架。原实现的主要问题不是功能太多，而是运行架构与问题规模不匹配，并且同时保存输入和派生板图，形成了两个互相竞争的事实来源。

本轮重构将系统改为静态 React 应用，保留已确认的实验行为与 LabNest 系列视觉语言。核心原则是：输入配置是唯一事实来源；板图、质控和用量全部由纯函数派生；只有用户手工改单作为最小差异保存。

## 由外到内的审查

| 层级 | 原设计问题 | 风险/代价 | 本轮处理 |
| --- | --- | --- | --- |
| 产品 | 设置变化后，旧板图可能继续显示和导出 | 技术人员可能导出与当前表单不一致的板 | 改为单向派生；布局生成后，配置变化会即时重算 |
| 交互 | 清空样本还要二次确认；保存状态显示“未保存”但后台正在自动保存 | 打断连续录入，状态语义不准确 | 样本清空改为直接操作；状态改为“正在自动保存” |
| 页面 | 一个 877 行组件同时负责状态、持久化、排板、导出和全部 UI | 修改任一区域都容易波及全页 | 拆为壳层、设置、板图、反应体系、控制器和文档模型 |
| 状态 | 20 多个离散状态，加上完整 `plan` 的第二份状态 | 状态组合爆炸，容易出现过期派生数据 | 一个 `PlannerDocument` 保存输入；`plan` 使用 memoized 纯函数生成 |
| 持久化 | localStorage 保存完整 96/384 孔板数据，且同时保存输入 | 体积大、迁移复杂、输入与板图可不一致 | 仅保存输入、是否已生成和少量 `WellOverride` |
| 算法 | 384 孔渲染对每个孔再遍历全部孔；质控和配液反复 filter | 板数和样本增加后形成不必要的平方级扫描 | 孔位按行主序直接寻址；统计改为一次遍历建立计数表 |
| 运行时 | Next + Vinext + RSC + Worker + Cloudflare + D1/Drizzle + Auth | 冷启动、构建、依赖和维护成本都没有换来产品能力 | 全部移除，改为 Vite 静态站点 |
| 样式 | 引入 Tailwind/PostCSS，但页面完全使用手写 CSS | 无效依赖和构建步骤 | 移除 Tailwind/PostCSS，保留现有 CSS 与配色 |
| 测试 | 测试大量匹配组件源码字符串和 SSR HTML | 重构即误报，无法保护真正业务规则 | 保留领域/Excel 测试，新增静态产物、紧凑存储和手工改单测试 |

## 新架构

```text
用户输入
   ↓
PlannerDocument（唯一持久化事实）
   ↓ normalize
PlanInput
   ↓ planCnvLayout（纯函数）
基础板图
   ↓ applyWellOverrides（少量手工差异）
当前板图
   ├─ validatePlan → 质控提示
   ├─ calculateReactionRequirements → 配液需求
   ├─ PlateWorkspace → 页面显示
   └─ exportWorkbook → Excel / Well + Sample
```

边界划分：

- `lib/cnvPlanner.ts`：排板领域规则和质控，不接触浏览器或 React。
- `lib/reactionCalculator.ts`：反应体系计算，不接触 UI。
- `lib/exportWorkbook.ts`：导出适配器；Excel 引擎只在点击导出时加载。
- `app/plannerDocument.ts`：默认文档、输入规范化和一次性旧数据迁移。
- `app/usePlannerController.ts`：把用户操作翻译为文档变更，并组合派生结果。
- `app/components/*`：设置、板图、反应体系三个明确视图。
- `app/CnvPlanner.tsx`：只负责页面骨架、顶栏和摘要。

## 删除的过度设计

- Next.js、Vinext、React Server Components。
- Cloudflare Worker 本地运行壳、Wrangler 运行配置。
- D1、Drizzle schema、示例 API。
- 未使用的 ChatGPT OAuth 辅助代码。
- Tailwind、PostCSS 和未使用的模板图标。
- 对历史版本分别重建整块板图的多路迁移逻辑。
- localStorage 中完整板图的重复副本。

安装过程从依赖树中移除了 321 个包。部署产物现在是 `dist/` 中的静态 HTML/CSS/JS；常规界面包约 81 kB gzip。较大的 Excel 包被拆成独立异步 chunk，只有导出时才下载。

## 保留的必要防线

以下检查不是“过度防御”，因为它们直接阻止实验或数据错误：

- multiplex 同孔 Reporter 重复时标红并禁止生成。
- 复孔必须为 1–8，且复孔不跨行、横向连续。
- 96 孔 A–H 纵向八道上样；384 孔两轮隔行顺序保持已确认规则。
- 每板重复对照，检查缺孔、重复复孔编号和手工编辑孔。
- 反应组分不得超过总体积，余量范围有明确提示。
- “重置整个工具”仍保留确认，因为它会同时删除所有本地实验配置。

## 性能模型

- 板图渲染：由每孔 `find` 的 `O(W²)` 改为行主序数组直接寻址 `O(W)`。
- 质控：由每个样本/反应组反复扫描所有孔改为一次建表后查询，主体为 `O(W + S×R)`。
- 配液：由每个反应组和样本分别扫描所有孔改为一次扫描，主体为 `O(W + S + R)`。
- localStorage：由“输入 + 全部孔板”改为“输入 + 少量改单”，常规保存量不再随空孔数膨胀。
- 首屏：无 SSR/Worker 启动；Excel 库按需加载。

在本机对 1,002 个样本/对照、6 块 384 孔板（2,304 个物理孔）的单次烟雾基准中：排板约 2.61 ms、完整结构质控约 2.08 ms、反应用量统计约 0.77 ms。该数字只用于发现数量级退化，不作为不同设备间的性能承诺。

## 兼容性与验证范围

保留并自动迁移旧版 localStorage（v1–v5）的主要配置；v5 中标记为手工编辑的孔会转换为差异记录。旧版整块板图不再作为事实来源，而是按当前确定性规则重建，避免把历史过期板图继续带入新版本。

自动测试覆盖：duplex/multiplex、Reporter 去重、Assay ID 可空、96/384 孔顺序、跨板对照、复孔连续性、手工改单不污染基础板图、反应体系、Excel 工作表与仪器列表、紧凑持久化及静态构建。

## 有意保留的后续观察项

`xlsx-js-style` 的导出 chunk 仍较大（约 318 kB gzip）。目前它不会影响首屏，且现有格式化工作簿与仪器列表已经有测试保护，因此本轮不为追求数字好看而冒险替换。若未来需要离线包极限瘦身，可评估只写 XLSX 的更小实现，并以现有工作簿作为金标准逐表对比。
